# 0.2.0-alpha.6 — owner decisions (day 0)

Recorded: 2026-10-18. These decisions were taken by the project owner at the
start of the alpha.6 phase, on the recommendations of the 2026-10-17 workspace
assessment and its alpha.6 plan (both in the owner's assessment folder, not
published). Decisions 9 to 14 are the roadmap's; 11-b and 15 to 19 were added
while the plan was checked against `main`. Each one names the work it
unblocks. Later phases record their own decisions in this directory.

| # | Question | Decision | Unblocks |
| --- | --- | --- | --- |
| 9 | When realm-wide or client-wide sign-in budgets are exhausted, does everyone get `429`, or do known devices keep a quota? What defaults do the new token and pre-authentication budgets use behind trusted proxies? | **Known-device quota.** Networks, devices and identifiers with a successful sign-in in the last 30 days keep a separate quota; everyone else gets `429 rate_limited` with `Retry-After`, and `proudauth_rate_budget_utilization` feeds an alert near the cap. No CAPTCHA and no proof-of-work. `token_per_client` rises to about 2000 per minute, consistent with `login_per_client`, and for public clients only failed grants count against it; the pre-authentication budget is about 300 per minute per IPv6 /64 or IPv4 /32. Both are re-measured with identity-bench before the tag. | Network-normalized budget keys and known-device quota; pre-authentication budgets |
| 10 | What is the consecutive second-factor failure policy? | **Growing backoff, a notice at 20, code factors off at about 100.** A persistent per-account counter of consecutive code-factor failures resets on success and grows the backoff across windows; the account owner receives a mandatory security notice at 20 consecutive failures; code factors (TOTP, HOTP, e-mail and SMS codes, recovery codes) are disabled at about 100 while passkeys and e-mail-verified recovery stay usable, so an attacker cannot cause a permanent lockout (SEC-006). The current-password check of a password change runs under the sign-in failure budgets. | Second-factor failure ceiling |
| 11 | Does a password reset revoke user-owned personal access tokens and API keys, or put them on hold? | **Revoke.** Password reset, password-compromise marking and assisted recovery revoke the user's active personal access tokens and user-owned API keys in the same transaction and name them in the security notice; there is no hold state. Introspection treats a user-owned credential created before the user's latest `token_revocations` record as inactive. | PAT revocation |
| 11-b | Does minting a personal access token require second-factor proof when the account has MFA? | **Yes.** `POST /me/personal-tokens` requires factor authority when the account holds an enrolled second factor; a password-only or remembered-device session cannot mint one. MCH-006 as written does not require this; it is hardening. | PAT revocation |
| 12 | Does `POST /me/organization-grants` run a full consent-coverage check, or is it limited to first-party clients? | **Full check.** The shared consent-coverage helper (live consent at the current terms version, otherwise a realm or organization pre-authorization, `offline_access` always needing the user's own consent) runs before the grant is created, `ConsentID` is set so consent revocation cascades, and `token_policy.max_session_age_seconds` applies. Missing coverage returns `403 consent_required`. | Organization-switch consent |
| 13 | Is DPoP/mTLS binding of refresh families applied whenever the first issuance was bound, and what happens to families issued before the change? | **Bind whenever the first issuance was sender-constrained**, whatever `require_dpop` says. `refresh_families` gains nullable `cnf_jkt` and `cnf_x5t_s256` columns, set at the first issuance and enforced at every rotation; a mismatch or a missing proof returns `invalid_grant`. Families issued before the change keep today's behaviour until they expire. The optional `dpop_jkt` authorization-code binding ships in the same change; DPoP-Nonce stays deferred (issue #37). | Sender-bound refresh families |
| 14 | When an approved dynamic registration changes user-visible metadata, is the change rejected or re-queued for approval? | **Re-queued.** Changes to `client_name`, `redirect_uris`, `post_logout_redirect_uris`, `grant_types` or the logo, client, policy and terms URIs return the client to `pending` and suspend it; before and after values go into the audit record; approve takes the reviewed version and returns `409` if the client changed since review. | DCR re-approval |
| 15 | What does `GET /oidc/logout` do when the `id_token_hint` does not match the browser's cookie session? No hosted UI exists for a confirmation page. | **Leave the session alone and answer `400 invalid_request`.** The cookie session ends only when the hint's `sid` equals it or its `sub` is the session's user; a relying party that cannot present a matching hint uses `POST`. | Distinct `typ` for JARM and signed UserInfo; logout hint |
| 16 | Does the issuer-only `aud` rule for `private_key_jwt` client assertions apply to new realms only, or to every realm? | **Every realm.** `aud` must be a single JSON string equal to the issuer for all `private_key_jwt` clients, and always for fapi2 clients; a realm setting (`client_auth.allow_endpoint_audience`, off by default) re-admits the token-endpoint URL and array audiences for older clients. The roadmap's default covered new realms only; with no external users the stricter rule costs nothing. | fapi2 client-assertion audience |
| 17 | How are the alpha.6 changes merged: one integration branch as in alpha.5, or a pull request per item? | **Hybrid.** Each work item is its own branch and pull request with a regression test. The budget chain that changes runtime behaviour (network-normalized keys and known-device quota, pre-authentication budgets, audit and metrics caps) lands on `alpha6-integration` and merges into `main` once, after the benchmark comparison. Everything else merges to `main` directly, including the migration runner, the DDL lint and the limiter core that later items depend on. Merges use `gh pr merge --admin` as before, because the sole owner cannot approve their own pull requests. | Every alpha.6 pull request |
| 18 | What do the alpha.6 Known limitations say? | The alpha.5 text minus the line on full-address budgets and the single token-endpoint budget, which alpha.6 removes. It keeps: not independently reviewed or certified (SEC-018, QA-005); the Go and Node SDK verifiers need a restart after an emergency rotation until SDK 0.3.0; administrators of different organizations are not separated from each other everywhere until alpha.7 and alpha.8; the worker runs one sequential loop until alpha.7. The owner reviews the final wording in the release pull request. | Release preparation |
| 19 | Are the identity-bench comparisons run with the new budgets raised, as alpha.5 ran with budgets at 1,000,000, or at the new defaults? | **Raised in the bench configuration and documented** in benchmarks.md, so the comparison measures throughput rather than `429`s; a separate short scenario shows that the pre-authentication budget answers `429` with `Retry-After` at the defaults. The gate: `password-login`, `refresh`, `client-credentials` and `introspection` regress no more than 10% against the alpha.5 baselines (identity-bench has no `token` scenario). | Pre-authentication budgets; alpha.6 exit gate |

No tag is created without the owner's explicit instruction; the alpha.6 tag is
cut only after the release dry run passes and the owner has approved the
CHANGELOG.
